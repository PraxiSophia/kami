## Scope, evidence and authority

This is an independent planning review of `Language_And_Network_Stack_Decision.md` (architect) and `../planning/Language_Implementation_Assessment.md` (senior developer), not a review of working software. I read both in full, the proposed canonical requirements and communication design, the pre-existing architecture/planning drafts listed under Sources, and the three earlier requirements-gap analyses. The requirements remain proposed; none of the stack recommendations is an approved specification. No build, dependency installation, deployment, crypto audit, interoperability test or cross-network experiment has been performed for this review. Upstream source observations describe inspected moving sources, **not** a pinned dependency, Kami integration, measured reachability or production assurance. Citations below distinguish local proposals [L], earlier analyses [G], and upstream documentation/source [U].

The testable first-message (FM) claim, **conditional on Product approval**, is two distinct, online, explicitly verified CLI devices on separate networks exchanging bounded private text, direct where demonstrably viable and automatically via an endpoint-authenticated live relay when direct is blocked. Sender outbox is durable before send; recipient inbox/dedup is durable before device ACK; retry/path switch preserves logical ID and content binding and does not duplicate display. A missing ACK means **unconfirmed**, not undelivered. This is not the proposed full v0.1 release: it excludes durable remote mailboxes, org/project discovery, groups, artifacts and two agent adapters, which remain later requirements rather than canceled obligations. [L1][L2][L3][L4]

A live Noise-protected peer stream can protect text through a forwarding relay when the *inner* session authenticates the intended device. It does **not** produce a portable signed recipient ciphertext or a mailbox envelope; independently negotiated session ciphertext is not identical across paths. Product's J2 “same ... ciphertext” and the architect's signed HPKE/mailbox trace conflict with the developer's online live-channel proposal. Both comparison documents identify the conflict; neither resolves it by technical preference. Product/security must decide the claim before stack selection, or the experiment must explicitly investigate asynchronous message encryption too. A self-signed descriptor/Peer ID proves key possession, not a verified person or project authorization. [L3][L4][L5][L6][L7]

## Independent findings and reconciliation

1. **Library capabilities, not a finished FM path (verified / inference).** Rust's upstream DCUtR and relay examples compose Tokio, TCP/Noise/Yamux, QUIC, Identify, relay client/server and DCUtR; rust-libp2p 0.57.1 metadata exposes these as separately selected features (none enabled by default). Go's upstream relay handles reservations/circuits and exposes distinct reserve/connect authorization hooks. These establish plausible component availability, not matching feature graphs, cross-language wire interoperability, a Kami protocol, secure enrollment, failure recovery or real NAT success. The architect's release/version notes and the senior developer's moving-branch examples are snapshots; pin exact toolchain, crate/module, features, transitives and security configurations and build the selected targets before promoting any claim. A docs.rs documentation-build failure is not an application build failure. [U1][U2][U3][U4][L8][L9]

2. **Rust relay admission is an actual discriminating risk (verified / unknown).** The inspected Rust relay `Config` offers circuit/reservation counts, rates, duration and byte caps, but no Go-style `AllowReserve`/`AllowConnect(src,dst)` application callback; Go's inspected relay checks both distinct hooks before accepting reservations/connects. The Rust behaviour emits accepted/denied events, but an event *after acceptance* is not evidence of a pre-forward authorization gate. A connection-level allowlist might restrict peers but is not equivalent to destination/project-scoped permission; behaviour composition or an outer gate may be possible, but no supported, race-free equivalent was demonstrated. Demand negative tests for unauthorized reservations and unauthorized source→destination circuit setup, with rejection before useful forwarding and a documented maintenance strategy; do not presume a fork is authorized. Conversely Go's hooks are not Kami membership policy until wired to a trusted source and tested. [U2][U3][L7][L8]

3. **Relay limits may invalidate the nominal frame (verified / decision).** The inspected Rust relay default is 128 KiB per circuit, with a two-minute circuit duration; the draft Go CLI plan proposes a 256 KiB *entire* application frame, while the prior full-release analysis proposes a 256 KiB *encrypted payload*. These are not compatible approved limits. A relay carries security/mux/framing bytes and possibly retries/ACKs within its circuit budget; even raising the nominal circuit limit to exactly the app-frame size would be insufficient. The Go default resource budget also needs inspection on the **pinned** version; do not treat this as only a Rust problem. Approve text, encoded frame, relay byte/duration, queue, attempt and deadline bounds as separate quantities, reserve overhead and test exact/over-limit in both directions including ACK and reconnection. These values cannot be imported from the full-release proposal. [U2][L8][L9][G2]

4. **Direct-first and relay-first are materially different (verified / recommendation).** The architect proposes parity trials with separate-network direct success and automatic fallback; the developer proposes a Rust-first sequential trial with Go as baseline. Either can answer FM only if the same approved topology, trust, protocol, bounds and faults are used. Explicit public address exchange/TCP dialing can succeed when a direct candidate is reachable; it is not general hole punching between two private NATs. DCUtR, as specified, *starts over an established relayed peer connection*, synchronizes a direct upgrade and retains relay on failure. Thus a DCUtR trial cannot be reported as proof that a direct-first TCP timeout followed by relay has NAT traversal. Record the connection actually carrying each application frame and ACK, not just a peer-level connected state or a pre-send probe. A third independent relay must already be reachable outbound from both online endpoints; a relay-only switch or localhost cannot prove automatic fallback. Neither stack solves an HTTPS-only authenticated proxy merely by using TCP/443. [U1][U5][L3][L4][L10]

5. **Confidentiality and identity depend on integration, not memory safety (inference).** Rust safe code reduces memory-lifetime and data-race exposure at the application boundary; Go avoids many manual memory errors; C/C++ requires tighter native lifetime/parsing review. None supplies the approved trust ceremony, sender/device binding, replay policy, key protection, transport-to-relay-to-endpoint security proof, database confidentiality, authenticated receipt or authorization. A relay must authenticate its own public endpoint; Bob and Alice must independently verify each other's pinned endpoint identity over the inner channel. QUIC/TLS is not “Noise over QUIC”; a security configuration and identity binding must be checked per selected transport. Sentinel-negative logs/storage checks are bounded leak inspections, not proof of E2EE. [L1][L2][L6][L7][U6]

6. **Delivery and portability are equally gating (documented / unknown).** All three stacks must support atomic sender enqueue before network I/O, recipient inbox+dedup+receipt fact before ACK, idempotent re-ACK after crash, same-ID/different-content rejection, authenticated late-ACK reconciliation, safe diagnostics and finite replay retention. Neither Tokio nor goroutines plus SQLite provides these automatically. In Rust, a blocking SQLite/keyring call in the Swarm owner can starve relay/session progress; isolate bounded storage/key work, test cancellation after commit and backpressure. In Go, contexts and `database/sql` also need cancellation/commit-result and worker-lifecycle tests. Stock SQLite does not encrypt histories, WAL or backups; availability of a protected headless key backend and selected at-rest policy on each claimed OS remains unproven. Cross-platform compile alone does not validate native linkage, keyring access or crash durability. [L2][L3][L8][L9]

7. **C/C++ needs a genuinely comparable route (verified / unknown).** The inspected cpp-libp2p README lists TCP, SECIO/plaintext, Yamux/MPlex and Identify, not a proven Noise + Circuit Relay v2 + DCUtR assembly; missing README entries do not prove impossible implementation, but a cpp-libp2p parity claim lacks evidence. Its C++17 description and C++20 README disagree. libdatachannel is a concrete C++/C-ABI WebRTC data-channel/ICE/DTLS/SCTP option with native TLS/ICE/SCTP dependencies and external signaling; TURN is a different live relay, not libp2p Circuit Relay v2. It needs authenticated candidate/SDP and DTLS-fingerprint-to-Kami-device binding, credential lifecycle, TURN deployment and the *same* durable message/ACK tests. C ABI availability does not make the underlying implementation pure C or simplify packaging automatically. No maintained C libp2p combination meeting FM was established. Do not exclude a demonstrated native option categorically, but do not select it for perceived raw performance without measurements and a concrete constraint. [U7][U8][L8][L9]

8. **Future extensibility is not an FM tie-breaker without a selected future protocol (inference).** OpenMLS is a Rust group-crypto candidate; its existence does not choose MLS, a provider, offline epoch handling, security review or a Python API for Kami. Python adapters can initially call a versioned, authenticated CLI/IPC interface in any language; native bindings in Rust (PyO3), Go (cgo-export/C shim) or C/C++ carry ABI, packaging, lifecycle and cancellation work. Keep one profile/engine owner; defer SDK/daemon/native extension design until interfaces and agent authorization are approved. Neither HPKE/MLS availability nor language popularity justifies adding mailbox/groups to FM. [L1][L2][L8][L9][G1][G3]

## Feasibility verdict and bounded decision rule

**Present verdict:** Rust + Tokio/rust-libp2p (TCP/Noise/Yamux, relay v2) and Go + go-libp2p are *plausible* for a restricted, online two-CLI FM, but neither is **demonstrated feasible for Kami** across separate networks, approved network profiles, relay admissions, protected storage and crash/receipt constraints. Go is the provisional documentation baseline, not a passing implementation. Rust offers an evidence-backed component set and safety benefit, not a proven shorter schedule. C/C++ with cpp-libp2p is not presently an evidence-backed equivalent; libdatachannel/WebRTC is a different architecture worth a separate gate if a mandatory network profile defeats the chosen libp2p design. No measured latency, reachability rate, build/packaging success, license clearance or team proficiency is available. An unconditional Rust migration or an unconditional Go endorsement would overstate evidence. [L4][L8][L9]

**Recommended authorization, not executed:** First freeze G0 Product scope and G1/G2 trust, frame/receipt/state and key/history policy; G3 approves target OS/architecture, two real independently controlled endpoint networks, separate reachable relay, approved resource/time budgets and fault controls. Then run three **minimal, checkpointed** experiments, stopping on a hard failed gate rather than expanding a POC into a product:

| Experiment | Minimum reproducible evidence | Pass / stop |
|---|---|---|
| A. Pinned integration and security/admission | Pin Rust/toolchain/libp2p features and a Go baseline candidate; independent secure endpoint + relay processes; versioned bounded frame/ACK; exact verified device↔Peer ID binding, wrong/changed key rejection, no downgrade, relay reservation and source/destination denial, circuit budget including overhead; actual builds/run on every claimed platform; record native dependencies and an identified backup maintainer. | Pass only when a selected candidate builds/runs and the intended endpoint authenticates through relay; unauthorized forwarding is denied and caps suffice. Stop on missing mandatory ACL, unsupported build/key provider or unreviewed crypto. If Go is not actually exercised, call it a documentary baseline, not comparative measured evidence. |
| B. Local durability/async seam | One minimal versioned message and receipt; sender crash after enqueue, receiver crash after inbox commit before ACK, restart/re-ACK, duplicate and content conflict, store-full, unavailable protected key, late ACK; bounded Swarm/Go worker liveness under store latency. | No send without durable outbox; no ACK before atomic inbox/dedup fact; one display, honest unconfirmed outcome, no plaintext-key fallback or stuck unbounded queue. Approval of a lab encrypted-volume profile is not proof of application-at-rest encryption. |
| C. Genuine reachability/path switch | Two endpoint hosts on independently recorded networks and a third relay; directly eligible profile actually carries Kami frame **and ACK** over direct; in a separately controlled fault direct becomes unavailable while relay remains reachable and default `auto` delivers through authenticated circuit; lost-ACK, relay quota/outage and reservation renewal; optionally separate relay-first DCUtR/QUIC trial if an approved NAT profile requires it. | Preserve logical ID/content binding and one durable inbox/display; provide per-frame connection/path, endpoint-authentication, fault, timing and status evidence against preapproved bounds. No localhost, forced-relay, ping-only or unknown-NAT substitution. Report unsupported profiles, not universal reachability. |

Do **not** adopt the senior developer's five-engineer-day figure as a schedule promise: it is a proposed stop budget that excludes host provisioning and owner review; approve or revise it with named maintainers and checkpoint scope. The architect calls for Go/Rust parity; the developer suggests Rust first with a Go comparison only if Rust fails. Reconciliation: run the cheap build/API/security gate on both if comparative language selection is the goal; carry identical acceptance fixtures into a *bounded* second implementation only when the outcome would change the decision. Record “not tested” rather than inferring Go parity from Rust results. If Rust fails a Rust-specific supported-API/packaging gate, compare Go on that exact fixture; if both fail identical egress or approved policy constraints, return to owners rather than switch language blindly. If both pass, prefer the maintainable lower-risk stack against actual integration, packaging and operator results; select Rust only if its demonstrated benefits and named maintainers outweigh migration cost. If direct cannot be shown on any **approved direct-eligible profile**, FM fails irrespective of successful relay; revise network profile/stack or seek an explicit narrower Product claim. Successful POCs are feasibility evidence, **not** FM qualification or full-v0.1 release approval. [L2][L3][L4][L8][L9]

## Decisions requiring owner approval

- **Product (G0):** FM name/online-only exclusions versus full v0.1; whether same *logical* content rather than portable ciphertext is sufficient; what counts as direct when a relay-assisted DCUtR upgrade was used; supported networks/OS and any narrowed public claim.
- **Security/architecture (G1/G2):** enrollment verifier and exact device↔transport binding, changed-key/block behavior, approved live cipher/QUIC profile and no-downgrade rule, private-key/history/WAL protection, per-frame/content IDs and authenticated receipt schema, crash sync/replay/late-ACK semantics; a later asynchronous E2EE/MLS suite is a separate decision.
- **Network/operator (G3):** third-relay ownership and outbound reachability, source/destination admission/quotas/circuit overhead, reservation renewal, direct-first versus relay-first DCUtR, candidate/IP disclosure, finite deadlines and unsupported enterprise egress.
- **QA and maintainers (G3/G4):** parity fixtures and exact build/target matrix, fault/sample thresholds, protected evidence retention, Rust/Go ownership and budget. No security certification, production revocation or runtime benchmark is implied by a document review.
