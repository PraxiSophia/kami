# Communication architecture

Status: Draft — Pending Approval

## Authority and milestone boundary

The owner has selected Rust as Kami's sole implementation language. This document proposes a Rust-native communication architecture, not approved technical interfaces, an implementation authorization, or evidence that Kami works. `../Kami_Project_Requirements.md` remains proposed; `../Kami_Communication_Design.md` separates direct connectivity, live forwarding and durable offline delivery. The online First-Message Milestone (FM) is the narrow contract reconciled in `../planning/Master_Execution_Roadmap.md` and proposed in `../planning/First_Communication_MVP.md`; the latter's phrase “same ciphertext” must be resolved as the same *logical ID and content binding*, not identical Noise session bytes, before an FM wire contract is approved. `Architecture_Review.md` R1–R6 records the historical conflicts; the three language evaluations are historical inputs, not the current language decision.

FM covers two independently initialized, explicitly verified, online, human-operated CLI devices (one per participant), one bounded private text message, authenticated direct P2P where viable and automatic authenticated live-relay fallback when direct is blocked, durable local sender outbox and recipient inbox, same-ID retry/dedup, a validated recipient device ACK, and safe diagnostics. FM does **not** provide a directory, tenant administration, durable remote mailbox, group fanout, artifacts, harness adapters/tasks, multi-device reconciliation, or production revocation. It is not full v0.1. Full proposed v0.1 still includes organizations/projects and invitations, permission-aware discovery, persistent encrypted offline mailboxes, small mixed groups, encrypted artifacts, two distinct harness adapters and recipient-side execution authorization. Those require separate approval and validation, not deletion from the roadmap.

## Proposed Rust-native topology and ownership

```text
CLI A -- engine + SQLite outbox -- rust-libp2p TCP/Noise/Yamux -- CLI B + SQLite inbox
  |                             direct peer stream                ^
  +-- same logical ID -- Circuit Relay v2 (separate live process) --+
       both clients online; inner authenticated Noise session ends at B

Later only: directory/authorization service; separately specified durable
ciphertext mailbox; group fanout/artifacts; locally authorized harness adapters.
```

One Rust client engine, run under Tokio, owns each profile and its libp2p Swarm; a distinct Rust relay executable/process owns its own identity, reservations and ephemeral forwarding. Neither relay admission nor an authenticated connection to the relay authenticates Bob: A validates the *inner* secure peer session against Bob's locally verified device-to-Peer-ID binding. The relay cannot be treated as an inbox. Manual exchange of bounded public descriptors over a separately trusted channel and explicit fingerprint verification suffice only for the controlled FM authorization policy; a self-signature proves key possession, not real-world identity or project membership. No public DHT publication or presence guarantee is implied. Both clients must have outbound reachability to the separate relay before a circuit can be used; Bob must be online and have an active reservation.

Proposed separation: CLI handles bounded input, safe text/JSON rendering and process lifecycle; protocol defines transport-independent logical IDs, frame/ACK fields and validation; identity owns protected keys, pinned peer records and trust decisions; delivery owns outbox, retry and receipt facts; the continuously polled rust-libp2p Swarm owns connections, session/path observations and Circuit Relay v2 client behavior; SQLite owns atomic local state transitions. Use bounded command/event channels between the Swarm and delivery owner. Keep blocking SQLite and key-provider operations off the Swarm poll path, with bounded workers, explicit cancellation and commit-result reconciliation; aborting a Tokio caller must not imply a committed send was undone. One active owner per profile; exited CLI processes retain pending outbox state but cannot retry in the background. Reopen the profile and reconcile before retrying. These are interfaces to approve, not asserted crate APIs.

## FM delivery trace

1. Initialize A and B independently with protected device transport keys, opaque participant/device IDs and profile stores. Each imports the other's public descriptor as pending, checks a fingerprint independently, pins the exact binding, then permits messages under the narrowly approved FM policy. Pin and authenticate the relay identity separately. A changed/unknown peer key blocks sends and inbound acceptance pending explicit re-verification; never silently replace it or downgrade security.
2. A validates the verified recipient and bounded UTF-8 input, assigns an opaque stable message ID, binds its immutable sender, recipient and content, and commits an outbox record in SQLite before network I/O. Local history, WAL, backups and private-key storage have separate confidentiality requirements; Noise does not encrypt local files.
3. A tries an approved, finite direct TCP + Noise + Yamux peer path, then automatically uses a Circuit Relay v2 circuit if direct is unavailable while the relay and B are reachable. On either path, the inner Noise handshake authenticates B's Peer ID and the pinned device record. The same versioned application message/ID travels on whichever secure stream succeeds; per-session ciphertext can differ. No custom encryption layer or signed asynchronous envelope is assumed for FM.
4. B validates session identity, frame version/bounds, sender, recipient, trust state and immutable-content consistency. B commits one inbox/dedup/receipt fact atomically and only then emits a session-authenticated per-device ACK. Duplicates with the same content return the prior receipt without a second visible event; same ID with changed content is a conflict. A marks `device_delivered` only after verifying the ACK issuer, correlation and outbox match. Missing/invalid ACK means unconfirmed, not proven absent; path switch reuses the ID.
5. If B is offline, direct and relay fail, reservation/quotas reject, or local storage/key access fails, report a bounded explicit non-success outcome and retain the committed outbox according to approved policy. No `mailbox_accepted` event exists in FM; an online relay does not buffer after B disconnects.

Actual per-frame and ACK path must come from connection events, not a `--path` flag or a peer-level “connected” observation. Relay-only and loopback experiments are internal precursors, not the two-network direct-and-fallback milestone.

## Later services and boundary-preserving expansion

Full-v0.1 proposals require an authenticated, permission-scoped participant/device directory and organization/project policy; transactional ciphertext-only mailbox with enqueue/fetch/expiry and distinct `mailbox_accepted` receipts; group membership snapshot/authorized fanout and separate per-device delivery facts; encrypted artifacts with independent access and integrity policy; and locally authenticated adapter interfaces to two named harnesses with recipient-side authorization, approvals and task idempotency. An approved reviewed asynchronous E2EE construction and portable authentication/receipt scheme must precede offline mailbox use. Captured Noise stream bytes cannot be queued for later recipient decryption. Group fanout must not race a membership removal; direct optimization must follow authoritative membership commit. Agent messages are data, never permission to execute. MLS, multi-device history reconciliation, chunked resume and federation remain conditional or later according to the canonical priorities; none is bundled into FM.

## Risks and validation gates (all unverified)

- G0 Product: approve FM online-only boundary and correct the portable-“same ciphertext” wording; retain all full-v0.1 obligations separately.
- G1 Security: approve verifier/trust states, endpoint Peer-ID binding, Noise configuration and protected key/history/WAL/backup policy on named targets; reject wrong or changed keys on both paths. No particular keyring backend or crate version is validated. Security review must inspect endpoint termination, not only a plaintext-sentinel scan.
- G2 Protocol/storage: approve exact schema/version, receipt authentication, finite text/frame/retry/dedup bounds, SQLite journaling/sync/crash assumptions and late-ACK projection; show outbox-before-send and inbox-before-ACK across restart. Stock SQLite offers transactions, not automatic encryption.
- G3 Network/operator: pin Rust toolchain and rust-libp2p features/API compatibility, prove relay reservation and pre-forward source/destination authorization in the selected Rust integration, and reconcile encoded frames plus Noise/mux/ACK overhead with configured circuit byte/duration/rate limits. No Rust ACL callback, default circuit size, NAT success, QUIC or DCUtR integration is assumed to work. Run two endpoints on separate recorded networks and a third relay process: direct-eligible application frame and ACK, then controlled direct-blocked `auto` fallback with relay still reachable. Measure path, deadlines, capacity and unsupported egress rather than asserting performance.
- G4 QA/review: verify ACK loss, duplicate cross-path arrival, store/key faults, no-route, malformed/oversize frames, redacted diagnostics and ciphertext-forwarding boundary. A passing experiment is scoped evidence, not a production security, availability or full-v0.1 claim.

If approved network profiles require hole punching, investigate rust-libp2p DCUtR over an already established relay connection and QUIC under a separate explicit security/transport profile; neither is a prerequisite or implied capability of direct-first TCP dialing. If a required profile cannot meet direct/fallback, stop and return to owners rather than quietly claiming relay-only success. Numeric thresholds, crate pins, deployment scale and packaging remain unverified until agreed tests.
