# Independent architecture review — first-message milestone

Status: Draft — Pending Approval
Review disposition: Revision required before implementation authorization; no design, release, or security claim is approved by this review.

## Basis and review boundary

Reviewed the proposed requirements (`docs/Kami_Project_Requirements.md`), nonbinding communication design (`docs/Kami_Communication_Design.md`), the three prior analyses in `/home/phu/.hermes/kanban/boards/kami/outputs/requirements-gap-report/`, and all eight new Product, Architect, Senior Developer, and QA drafts listed below. This is a planning review of documents, not implementation verification: the repository has no application/package manifest or executable tests. Findings identify conflicts and conditions for approval, rather than selecting a design by fiat. Source line references below refer to the drafts as inspected for this review.

The product's *first-message* criterion is two live, verified human-operated CLIs exchanging one encrypted text with direct P2P when feasible and authenticated live-relay fallback, a durable receiver inbox, and a genuine device ACK (`docs/planning/First_Communication_MVP.md:13-24,49-76`). It explicitly excludes offline mailboxes, groups, artifacts, adapters, and tenant administration; this cannot be marketed as the full proposed v0.1 scope (`docs/Kami_Project_Requirements.md:187-221`). A relay-only path is a useful internal precursor, not completion of the first-message direct/fallback milestone (`docs/planning/First_Communication_MVP.md:135-147`; `docs/Kami_Communication_Design.md:405-431`).

## Findings requiring reconciliation

### R1 — Incompatible milestone topology and E2EE boundary (approval blocker)

`docs/architecture/Communication_Architecture.md:9-24,49-59` calls its *first-message* trace a deployment with organization/project creation, an identity/membership directory, per-device application ciphertext/signatures and a transactional offline mailbox; the trace submits when online delivery cannot be confirmed and requires queue restart/reconnect evidence. `docs/architecture/P2P_Connectivity_Design.md:20-35` likewise makes fresh directory membership and asynchronous ciphertext/mailbox fallback part of path selection. The Product draft expressly excludes those services/capabilities (`docs/planning/First_Communication_MVP.md:65-76,108-116`), while the CLI plan proposes manually verified descriptors and Noise-secured *live* peer streams without a mailbox or application ciphertext (`docs/planning/CLI_Implementation_Plan.md:26-35,74-88,199-211`). These are two distinct architectures, not interchangeable implementations of an agreed first-message contract. A Noise channel that terminates at the recipient through Circuit Relay can provide endpoint-to-endpoint live confidentiality, but it cannot be copied into a future asynchronous recipient-decryptable mailbox envelope. Conversely, per-device signed HPKE application envelopes add signing, serialization, key lifecycle and directory dependencies now (`docs/architecture/Identity_And_Encryption.md:17-21`; `docs/architecture/Messaging_Protocol.md:11-17`).

Recommendation: Product and security/architecture owners must first publish the named milestone's allowed services and precise confidentiality claim. If this first milestone excludes mailboxes, mark the architect's mailbox/directory/group trace as a *later conditional design* and specify how local manual peer authorization suffices for the limited test; if application envelopes are required from day one, revise scope, schedule, QA cases and dependency gates explicitly. Neither an unsigned plaintext application body inside a secure peer stream nor a signed ciphertext envelope should silently inherit the other's security or storage claims. Record the trust and nonce/replay properties of the selected reviewed construction and the exact endpoint at which each layer decrypts.

### R2 — Trust/authorization and revocation interfaces are not common (approval blocker)

The architect assumes deployment-scoped enrollment, project-scoped discovery, freshness/version proofs, gateway TLS/challenges, separate device signing and E2EE keys, and revocation checks at send/fetch (`docs/architecture/Identity_And_Encryption.md:9-15,23-35`; `docs/architecture/P2P_Connectivity_Design.md:20-31`). The developer instead assumes manually exchanged descriptors, pinning against the authenticated libp2p Peer ID, and relay allowlisting (`docs/planning/CLI_Implementation_Plan.md:26,74-80`). A descriptor self-signature proves possession of a key, not membership in a project or a human identity; an allowlist does not enforce tenant membership. Either model still needs authenticated first-contact verification, a proof-of-possession binding from participant/device ID to transport identity, changed-key behavior, and an authorization source for accepting inbound messages. In the manual model there is no defined authority or distribution path to revoke a verified peer promptly; it must not claim full revocation or ID-04 permission-aware discovery. In the server model an operator can substitute keys unless counterpart pinning/independent verification catches it. The draft requirements require counterpart verification and defined key rotation/revocation before production (`docs/Kami_Project_Requirements.md:101-110,164-171`); ID-06 is a proposed SHOULD, not automatic justification for omitting safe handling of compromised credentials.

Recommendation: freeze the milestone trust-state matrix (bootstrap, pending, verified, changed, blocked/revoked), whose proof is checked at direct and relayed session establishment and on subsequent sends, who may authorize a correspondent, how a compromised key is retired, and what an offline/unreachable authority means. Specify which narrower controls are acceptable only for an isolated demonstration and explicitly defer tenant and production revocation claims. Include wrong-device/peer-ID, changed-key, stale-auth, directory-substitution, and relayed-session tests. Require a concrete key-provider and local-history policy on the supported OS/profile; SQLite permissions alone do not encrypt history (`docs/planning/CLI_Implementation_Plan.md:172-175,181-197`).

### R3 — No single interoperable envelope, receipt, or race contract (approval blocker)

`docs/architecture/Messaging_Protocol.md:9-21` sketches a signed `kami.event.v1` per-recipient encrypted envelope, service-/device-signed receipts, deployment/organization/project/conversation IDs, and an optional group commit sequence. The CLI plan sketches `/kami/chat/1.0.0` length-prefixed JSON *inside Noise*, a smaller identity scope, receipt authentication by the pinned live session, and a future separately versioned offline wire schema (`docs/planning/CLI_Implementation_Plan.md:82-102`). These are not wire-compatible; a session-authenticated live receipt cannot automatically be stored/forwarded as a verifiable device-signed event. The Product criterion calls for the “same ... ciphertext” over both live paths (`docs/planning/First_Communication_MVP.md:37-41`), which is only meaningful for an immutable application envelope; stream-cipher transport ciphertext will differ by session and retransmission. Preserve one logical ID/content binding, not an unsupported claim of identical bytes on distinct secure channels.

The protocol draft says a race between signed expiry and device ACK is reconciled by recipient commit time and server records, possibly `delivery_outcome_unknown` (`docs/architecture/Messaging_Protocol.md:23-35`); the developer instead proposes preserving a locally terminal failure alongside `late_delivery_confirmed` (`docs/planning/CLI_Implementation_Plan.md:94-102`). QA requires monotonic terminal-state reduction (`docs/planning/Test_And_Validation_Plan.md:98-104,120`), and the prior acceptance proposal likewise says late events cannot regress a terminal state (`mvp-acceptance-criteria.md:49-62`). A sender timeout cannot prove nondelivery, and untrusted device clocks cannot decide the physical order of a lost ACK and expiry. Reconcile a fact ledger versus displayed projection: distinguish `delivery_unconfirmed` from a proven permanent rejection, define authenticated late ACK handling, permissible terminal revisions, duplicate ACK identity, and retention through the entire replay horizon. The group wording also differs: prior analysis says a group is “fully delivered” once every device has delivered *or a terminal state* (`mvp-acceptance-criteria.md:90-103`), whereas the protocol correctly distinguishes delivered from “complete with failures” (`docs/architecture/Messaging_Protocol.md:31`). Resolve in the later group contract; never call a failed recipient delivered.

Recommendation: approve one milestone-specific normative, test-vectored schema/state table with sender and receiver identity binding, version negotiation, framing/text/wire bounds, authenticated receipt issuer and scope, atomic inbox-before-ACK, content-ID conflict, retry ownership, clock/expiry semantics, and status vocabulary. Decide whether signed portable receipts and application ciphertext belong to this milestone. Publish compatibility/migration boundaries before multiple teams implement against these drafts.

### R4 — Networking feasibility and acceptance environment are underspecified (approval blocker)

Libp2p Noise, TCP/QUIC, DCUtR/hole punching and Circuit Relay v2 are conditional candidates, not proof of working combinations (`docs/architecture/P2P_Connectivity_Design.md:7-18,39-43`). The developer limits the initial stack to TCP, explicit address exchange and a separately running relay; it correctly declines to infer hole punching or CGNAT success from loopback (`docs/planning/CLI_Implementation_Plan.md:166-179,199-211`). P2P draft's race/stagger window of 2–5 seconds (`docs/architecture/P2P_Connectivity_Design.md:33-37`) is not the same policy as developer's direct-first 2-second budget plus 10-second foreground receipt wait (`docs/planning/CLI_Implementation_Plan.md:130-145`). Both are unapproved. A restricted network test in which direct routes fail but both endpoints have outbound relay access establishes fallback, not universal NAT traversal. A TCP-only stack may fail the chosen target NAT/egress profiles; neither TURN nor Circuit Relay is a mailbox or a guaranteed enterprise proxy bypass.

Recommendation: select a supported network matrix and explicit success semantics for “direct when possible,” including a demonstrably direct cross-network profile, a deliberately blocked direct profile, relay reservation and both clients' outbound reachability, candidate disclosure policy, finite attempt/fallback/ACK budgets, and an outage/no-route result. Run a pinned-version feasibility spike *before* committing to the libp2p/OS/crypto dependency combination, with a separate third relay process, two independent hosts/networks, actual path evidence, identity binding and failover tests. If the selected stack cannot meet a required target network, return to owners for a bounded alternative (WebRTC/ICE/TURN requires its own signaling/security/ops design); do not quietly count forced relay mode, localhost, or a fake transport as fallback proof. Service admission, rate/byte/connection limits, health, credentials, and ownership must be specified before accepting an exposed relay (`docs/planning/CLI_Implementation_Plan.md:122,199-211`).

### R5 — Durability, resource limits and security evidence are unclosed

Sender-outbox-before-send and receiver-inbox-before-ACK are well aligned across Product, protocol and developer drafts (`docs/planning/First_Communication_MVP.md:15-22,84-93`; `docs/planning/CLI_Implementation_Plan.md:92-102`; `docs/architecture/Messaging_Protocol.md:19-35`). But successful write/transaction is not a durability guarantee without defined SQLite journaling/sync settings, filesystem failure assumptions, crash boundaries and an atomic inbox/dedup/event commit. The developer's one-profile-owner process rule avoids concurrent state writers but leaves short-lived `send` without background retries: next launch resumes pending work (`docs/planning/CLI_Implementation_Plan.md:104-128`). Product's J3 says the local outbox is retained until terminal policy (`docs/planning/First_Communication_MVP.md:43-47`); tests and UX must distinguish retained-but-inactive from active retry. For first-message online-only, relay rejection cannot become mailbox acceptance. An ACK lost after receiver commit needs retransmission of the same ID and an idempotent ACK after restart.

Proposed numeric bounds conflict in units/start time: the prior acceptance document proposes 256 KiB *encrypted payload*, 24-hour mailbox TTL *from acceptance*, 10 attempts and 1 GiB local outbox (`mvp-acceptance-criteria.md:170-190`); developer proposes 256 KiB *whole frame*, local-enqueue absolute expiry and a foreground 10-second wait (`docs/planning/CLI_Implementation_Plan.md:82-86,143-145,193-197`). Neither is approved or necessarily appropriate for this smaller milestone. The proposed 95/100 per-path and online p95 ≤5 s under 20-device load are full-v0.1 candidate targets, not automatic first-message pass/fail (`mvp-acceptance-criteria.md:184-197`). Establish finite FM input/frame, outbox/inbox/dedup, attempts, time, clock-skew and service quotas, an explicit failed-full-store behavior, and measurable sample/threshold conditions before acceptance. Avoid an expiry cleanup that permits replay after dedup eviction.

Security inspection cannot prove E2EE merely by failing to find a known plaintext sentinel in relay logs (`docs/planning/First_Communication_MVP.md:88-95`; `docs/planning/Test_And_Validation_Plan.md:128,149-157`). Validate authenticated *endpoint-to-endpoint* termination, relay operator inability to obtain payload/key, negative key-substitution and forgery tests, transcript/receipt binding, and the reviewed library's exact configuration; inspect buffers, logs, traces, persisted data and crashes within a defined test boundary. Record metadata visible to relay and any directly connected peer. On-device plaintext, terminal output, WAL/backups and test evidence need a stated protection/retention policy; do not claim local encryption based on transport Noise or stock SQLite (`docs/planning/CLI_Implementation_Plan.md:181-197`).

### R6 — QA matrix must be split by named gate

QA's plan is a strong full-v0.1 coverage catalogue with explicit `not testable` and environment labeling (`docs/planning/Test_And_Validation_Plan.md:22-52,98-139`). It is not yet a standalone first-message release gate. E1 assumes discovery, mailbox, authorization/membership service, while the developer's FM has manual descriptors and no mailbox (`docs/planning/Test_And_Validation_Plan.md:43-50`; `docs/planning/CLI_Implementation_Plan.md:26-35`). TV-04 requires an artifact reference in a direct-delivery case though Product excludes artifacts (`docs/planning/Test_And_Validation_Plan.md:115`; `docs/planning/First_Communication_MVP.md:65-74`). C1 schedules portions of task-lifecycle TV-11 and ciphertext-only storage TV-17 without specifying which portions apply to online-only text (`docs/planning/Test_And_Validation_Plan.md:131-139`). TV-03 asks for ciphertext on *every intermediary boundary*, a test that needs explicit distinction between the live inner channel and application envelopes (`docs/planning/Test_And_Validation_Plan.md:114`). E3 direct reachable and E4 restricted must be demonstrated independently; E1 loopback is not cross-network evidence. The plan includes revocation and group tests as full-release obligations, not reasons to claim these FM features exist.

Recommendation: create a first-message AC-01–AC-10 to TV crosswalk that names exactly the approved FM topology, builds, OSes, fixture/fault controls, expected statuses, run counts and pass/fail thresholds. Separate E0/E1 unit/crash proofs from E2/E3 direct and E4 automatic fallback, and explicitly mark all mailbox/task/group/artifact cases excluded *for this milestone*, not passed. Add fresh-listener versus concurrent-profile-lock, ACK-loss-and-restart, changed key, no-relay/no-route, disk-full, duplicate across paths, malformed input and output-control-character cases. Record safe IDs/path/receipt sequence and prove the injected direct failure actually took effect. Keep the comprehensive C3–C5 plan for any future full-v0.1 qualification after the relevant contracts are approved.

## Alternatives and dependency/operations assessment

- Gateway/relay-only first: a sensible internal way to validate one encrypted delivery and durable receipt (`docs/Kami_Communication_Design.md:411-418`), but reject it as evidence for direct P2P or automatic fallback. If it becomes a named external preview, Product must approve a distinct scope and claims.
- Libp2p/Noise plus Circuit Relay: conditionally plausible for two *online* Go CLIs, with one transport stack and no broker; dependency pin, supported-platform/key-provider validation, relay reservation, inner-session authentication and real network proof remain prerequisites. It is not an offline mailbox E2EE solution.
- Per-device HPKE plus signatures: conditionally plausible for store-and-forward with a reviewed library, but base HPKE is not sender authentication or forward secrecy (`docs/architecture/Identity_And_Encryption.md:17-21`). Canonical signed bytes, key rotation, offline authorization, public directory and receipt keys enlarge the first slice; do not adopt solely to make a future mailbox easier without product/security agreement.
- WebRTC/ICE/TURN: a coherent alternative if libp2p cannot meet selected network targets, not a drop-in Circuit Relay substitute. VPN overlay would shift enrollment and operational dependencies to another control plane. Gossip/MLS, broker deployment, group fanout and two harness adapters have no first-message acceptance role; defer until separate decision packages (`architecture-options-tradeoffs.md:37-83`).
- A self-hosted relay still needs public reachability, certificate/key management, abuse controls, monitoring, capacity, upgrade and incident ownership. Even one service is an operational dependency and metadata observer. A durable mailbox later adds storage, replication/backup/recovery, queue authorization, poison handling, and an asynchronous crypto contract; these obligations cannot be obtained by turning on a relay flag (`docs/architecture/Relay_And_Offline_Delivery.md:5-15,30-39`).

## Required owner decisions and stop gates

1. **Product / scope:** approve a versioned first-message label, allowed online-only topology and precise exclusions versus the proposed full v0.1 (`docs/Kami_Project_Requirements.md:187-221`); resolve whether org/project directory and mailbox are later work. Stop if the first-message claim is required to include offline delivery, adapters or group chat without new requirements, dependencies and acceptance evidence.
2. **Security / identity:** approve initial enrollment/trusted-channel fingerprint ceremony, inbound policy, key/Peer-ID binding, changed/revoked-key handling, live E2EE boundary, cryptographic library and supported key/local-at-rest backend. Stop if sender authenticity, correct recipient, or relay opacity depends on unverified keys or bespoke unreviewed cryptography.
3. **Protocol / reliability:** freeze a single test-vectored FM wire/CLI and receipt/state contract; define attempt/expiry owner, late ACK versus terminal failure semantics, durable sync/restart boundary, dedup retention, text/frame caps, and error/JSON output. Stop if two endpoints cannot exchange and validate identical agreed fields or if a socket/relay event is mistaken for delivery.
4. **Network / operator:** choose and pin transport/direct/relay stack, address exchange and relay admission, supported OS and realistic network matrix, direct/overall budgets, capacity/quota limits, failure statuses and measured acceptance thresholds. Stop if cross-network direct evidence or automatic fallback evidence is missing, or if the relay cannot be reached in a claimed supported environment.
5. **QA / independent review:** approve an FM-only evidence crosswalk and execute it against actual code, with negative/security/privacy tests and redacted reproducible traces. Until implementation exists, all outcomes are proposed test plans, not passes. Later full-v0.1 gate separately needs the five release-blocking packages from `requirements-gap-report.md:6-182`: identity lifecycle; delivery/task lifecycle; groups; named adapters/A2A posture; and operational bounds. Jira/PR links and implementation review are required for an actual development completion under `AGENTS.md:27-54`, not created by this planning document.

## Handoff to roadmap reconciliation

The minimal conditional path is to freeze scope and security/receipt contracts; prove one honest, durable live delivery as a limited internal slice; validate the pinned direct stack and separate relay with independent cross-network evidence; then run the approved first-message matrix. Keep mailbox/asynchronous E2EE, tenant-aware discovery, groups, artifacts and adapters in separately gated later phases. The roadmap should explicitly resolve R1–R6 or carry them as approval blockers, not select one draft by omission. No implementation, build, deployment, security audit or real-network test was performed in this review.
