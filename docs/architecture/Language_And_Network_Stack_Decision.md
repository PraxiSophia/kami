## 1. Decision boundary and evidence convention

**Requirements/proposal:** The canonical requirements are proposed, not approved (`../Kami_Project_Requirements.md:1-7,223-240`); the communication design leaves the transport stack open (`../Kami_Communication_Design.md:389-403,450-461`). The reconciled first-message (FM) roadmap specifies two independently initialized, online CLI devices, explicitly verified identities, authenticated direct P2P when viable and automatic *live* relay fallback, a durable sender outbox and recipient inbox, stable logical ID, validated device ACK, retry/dedup and safe diagnostics (`../planning/Master_Execution_Roadmap.md:25-46,155-172`). FM excludes a durable remote mailbox, groups, artifacts and harness adapters; these remain proposed full-v0.1 scope, not canceled requirements (`../planning/First_Communication_MVP.md:49-76`; `../Kami_Project_Requirements.md:187-221`). The independent review identifies the incompatible application-envelope/mailbox and online-only FM drafts; do not merge them by implication (`Architecture_Review.md:14-38`).

No packages were installed, code compiled, NAT test run, or interoperation demonstrated in this task. The repository has planning documents, not a Kami implementation or dependency lockfile (`../planning/CLI_Implementation_Plan.md:18-20`). **Verified protocol boundary:** Circuit Relay v2 reserves finite live circuits with hop/stop and limited duration/data; the destination keeps a relay connection and an incoming peer dials its circuit address. Both endpoints then upgrade that *relayed connection* with their own security protocol [S1]. DCUtR starts from an existing relayed connection and coordinates direct dialing; if it fails, the relay remains usable [S2]. Thus a policy that tries direct addresses and then dials the circuit is distinct from relay-first DCUtR, and both need real connection/path observations. Hole punching does not guarantee success through arbitrary NAT, CGNAT, UDP denial or enterprise egress. A live circuit/TURN allocation is **not** a durable offline mailbox (`../Kami_Communication_Design.md:16-26,84-100`).

**Inference (relative ranking, not benchmark):** Both Rust and Go have documented libp2p building blocks for a native two-CLI online FM. Go has the smallest *planning-document* change because the existing implementation plan and roadmap conditionally prefer it (`../planning/CLI_Implementation_Plan.md:28-35,162-179`; `../planning/Master_Execution_Roadmap.md:48-58`). Rust is a credible peer candidate with memory-safety benefits for untrusted input, but its Swarm/event-loop integration, chosen key provider, SQLite confidentiality and target combinations still need validation. Neither language supplies product authorization, offline E2EE, persistent storage or reliable delivery merely by selecting libp2p. C/C++ with cpp-libp2p is not an evidence-backed lower-effort FM libp2p route; libdatachannel is a genuine WebRTC/ICE/TURN alternative at a cost of a different wire stack, signaling, native deployment surface and identity binding. Do not equate absence from a README with proof that code cannot implement a feature; it means the capability is **unverified** and needs a stronger demonstration before commitment.

## 3. Feasible two-network architecture, conditional on proof

**Recommendation:** For either libp2p language, use one pinned, explicitly configured transport/security/mux combination (candidate TCP + Noise XX + Yamux; test QUIC/TLS and DCUtR separately, not implicitly), two independently provisioned CLI device profiles on separate networks, and a third reachable self-hosted relay service with explicit authorization, reservation refresh, quotas and health. Manually exchange bounded public peer descriptors/address/circuit hints and independently compare fingerprints for this controlled FM; this is not permission-aware discovery, organization membership, or production revocation (`../planning/CLI_Implementation_Plan.md:26,74-80`; `Architecture_Review.md:20-24`). Both clients must reach the relay outbound. Bob must reserve before Alice can dial his circuit; an address alone cannot reserve for an offline Bob [S1]. Avoid public DHT publication of private identities. Pin the relay identity as well as Bob's endpoint identity, and validate the transport-authenticated Peer ID against the locally verified `(participant_id, device_id, key/fingerprint)` record on both direct and relayed connections. A Peer ID authenticates possession of the transport key, **not** a human, a project permission or a current authorization state. If the Peer ID/key changes, stop and require the approved explicit re-verification; never fall back to plaintext or an unverified relay path.

For the online-only FM, end-to-end peer Noise over the circuit protects live content from the relay *if* the inner Noise connection really terminates at Alice and Bob and keys are pinned [S1][S3]. Transport session ciphertext differs between direct and relayed sessions. The product draft's “same ciphertext” wording (`../planning/First_Communication_MVP.md:36-41,55-59`) conflicts with the roadmap's live-session proposal (`../planning/Master_Execution_Roadmap.md:48-58`): preserve the same immutable **logical message ID and content binding**, not identical wire ciphertext. If Product insists on portable application ciphertext/signatures already in FM, choose a separately reviewed asynchronous E2EE construction, change the FM wire schema and test plan, and re-estimate; do not claim Noise gives offline mailbox envelopes (`Architecture_Review.md:14-18,26-32`; `Identity_And_Encryption.md:17-21`). WebRTC/DTLS similarly needs endpoint fingerprint-to-device binding outside unauthenticated signaling; a TURN server is not Bob.

**Recommendation:** Transport adapter reports only session identity, path and frame-send outcomes. Application engine persists the versioned, bounded message/ID and outbox *before* sending, validates frame/version/identity/recipient on receipt, atomically commits inbox plus dedup fact before emitting an authenticated per-device receipt, and marks delivery only after receipt validation. Retry unchanged logical ID/content on another viable path after timeout or disconnect; duplicate arrivals return the prior ACK without second display. Sender timeout means delivery *unconfirmed*, not proof of no delivery. Choose crash-sync, receipt issuer binding, retry/deadline, local at-rest confidentiality, frame caps and dedup-retention rules at roadmap M1–M2 before implementation (`../planning/Master_Execution_Roadmap.md:80-102,133-172`). SQLite and Noise do not themselves encrypt local plaintext history. FM does not emit `mailbox_accepted`; an offline Bob or unreachable relay produces visible pending/unconfirmed/terminal status under the approved bounded policy. No harness invocation, task authorization or A2A compatibility is implied by receiving a text frame.

**Feasibility judgment:** Direct on an eligible recorded pair of *separate networks* plus fallback on another recorded pair with direct demonstrably blocked and outbound relay still reachable is architecturally feasible with either libp2p implementation, but unproven for Kami and not guaranteed across arbitrary networks. A forced relay-only flag, two localhost processes, or a direct attempt that was never eligible does not establish both acceptance paths. If all outbound traffic to the relay is blocked, neither selected libp2p variant can claim delivery. A real fallback proof needs two client hosts/networks **and a third relay process/service**, relay reservation/admission evidence, actual selected direct/relayed path, Bob-as-endpoint authentication, ACK ordering and same-ID dedup/restart evidence (`../planning/Test_And_Validation_Plan.md:37-52,110-121`; `Architecture_Review.md:34-46`).

## 4. Decision and minimal POCs (not performed)

**Recommendation:** Retain Go + go-libp2p as a *provisional implementation baseline*, not an approved choice or a claim that Rust is infeasible. Run a time-boxed Rust-vs-Go parity feasibility investigation before G1/G3 approval if the owner values Rust's safety/tooling enough to change the current plan. Require the same protocol, topology, target OS and measured pass/fail gates; do not compare a full Go application with a Rust hello-world. Reject cpp-libp2p as the first FM implementation *unless* a maintained, compatible Noise/relay-v2/DCUtR route is demonstrated with substantially less integration cost; keep C/C++ libdatachannel + self-hosted signaling/TURN as an alternative if **both** libp2p paths fail an approved network profile or browser-native interoperability becomes a requirement. This is a conditional ordering, not a performance or security ranking.

Smallest experiments, only after scope/permissions approval:

1. **Build/API and identity seam:** pin one Go and one Rust library/toolchain/feature set; compile a pair of independent endpoint hosts and a distinct relay on the selected Linux baseline, then build for every OS/architecture actually claimed. Negotiate one explicit Kami protocol ID, verified Peer ID-to-device binding and secure channel; reject changed key, unsupported protocol and plaintext downgrade. Record lockfiles, feature flags and actual API/version mismatches. For Rust, test 0.57.1 docs/build uncertainty against the chosen toolchain; consider 0.56.0 only after reviewing security/maintenance tradeoffs, not because docs.rs failed.
2. **Network reachability:** with two genuine networks, show an authenticated direct stream; then *without forcing the client into relay-only mode*, block direct while preserving outbound relay access and demonstrate automatic Circuit Relay v2 reservation, circuit dial, secure endpoint handshake and bounded path fallback. In a separately labeled exploratory run, enable Identify/AutoNAT/DCUtR and show whether relay-to-direct upgrade succeeds for specified TCP/QUIC NAT profiles. Collect selected path from transport events plus network fault proof; no universal hole-punch percentage is inferred.
3. **Delivery/storage seam:** send one benign text fixture through direct and circuit with a durable outbox-before-send, inbox/dedup-before-ACK, ACK loss/restart and same-ID retry. Show one recipient display, a verified receipt, an unconfirmed no-route outcome, explicit store-full/invalid-key outcomes and safe redacted traces. Inspect relay observability for a sentinel but do not call that alone a security audit. Apply the same assertions to both candidates or mark a candidate not tested.

Decision pass gate: supported client builds and secure identity binding work; direct and auto-fallback both meet *owner-approved* finite timeout/resource limits on recorded networks; relay cannot read test content under the inspected configuration; same-ID receipt/durability tests pass. A failure yields a documented network or integration limitation and an owner decision to change stack, target environment or milestone claim—not a quiet relay-only pass. Security review must approve the exact cryptographic configuration and local key/history protection separately. No acceptance times, success rates or throughput values are asserted here because no experiment ran and the draft numerical values are not approved (`../planning/Master_Execution_Roadmap.md:155-172`).
