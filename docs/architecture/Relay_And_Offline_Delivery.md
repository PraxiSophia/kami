# Relay and offline delivery

Status: Draft — Pending Approval

## Two services, two milestones

Rust is the owner-selected implementation language; this document proposes Rust-native service boundaries without claiming tested crate APIs or deployed infrastructure. The First-Message Milestone (FM), as reconciled by `../planning/Master_Execution_Roadmap.md`, has only two **online** verified CLI endpoints, local SQLite durability and a separate live Circuit Relay v2 process. Full proposed v0.1 also requires a transactional **durable encrypted offline mailbox**, which is deferred, not canceled (`../Kami_Project_Requirements.md` MSG-04 and §10; `../Kami_Communication_Design.md` §2, §5). Relay forwarding and offline acceptance are different facts: a reservation or circuit does not queue data and must never emit `mailbox_accepted` or `device_delivered`.

## FM live-relay contract and operation

A separate Tokio/rust-libp2p relay-server process owns a public relay identity, listener, active reservations/circuits, admission, resource limits and health reporting. Its client endpoints are two distinct Swarms using TCP + Noise + Yamux. Both clients must reach the relay outbound, and the recipient must maintain/renew a reservation while online. The sender dials a circuit under an approved finite budget and authenticates the recipient through an **inner Noise peer connection** against its pinned device-to-Peer-ID record. Relay-facing Noise alone would end at the relay and is insufficient. The relay may inspect routing metadata, IPs, Peer IDs, times, volume and circuit relationships, but must not require application plaintext or device private keys. This is a bounded live confidentiality claim conditional on security review, not anonymity or persistent E2EE.

Admission is unresolved: establish a supported pre-forward Rust mechanism rejecting unauthorized reservations *and* unauthorized source→destination circuits under the FM allowlist policy. Inspected Rust relay configuration exposes reservation/circuit limits but does not demonstrate an application callback equivalent to a project-aware per-circuit ACL; post-accept events do not prove denial before forwarding. A coarse peer allowlist cannot stand in for later organization/project authorization. No custom library fork or open public relay is approved. Test the exact pinned crate/version/feature graph and prove denial before allowing an exposed listener; otherwise stop for an owner decision. Separate operator limits must bound reservations, circuits, rates, connection counts, circuit duration and bytes, including Noise/mux/frame/ACK overhead. Do not assume a library default circuit budget can carry the proposed message size. Confirm reservation renewal, relay restart behavior, quota refusal, operator key protection, logging/redaction and capacity under load. Numerical settings and relay performance are not verified.

On direct-path failure, `auto` sends the **same logical message ID/content binding** over the authenticated live circuit, within approved attempt and overall deadlines. Fresh channel ciphertext is expected on each connection. Recipient's SQLite inbox/dedup/receipt transaction precedes its session-authenticated ACK; sender verifies ACK before device-delivered status. Lost ACK, circuit drop or duplicate direct/relay arrival retains one durable recipient item and permits idempotent re-ACK. If the recipient is offline, no reservation exists, both routes fail or relay refuses service, keep a visible local pending/unconfirmed or terminal outcome under the approved policy. An exited short-lived CLI does not continue retries. A successful circuit, socket write or relay event is never proof of device delivery.

## Later durable-mailbox proposal (not FM)

A separately specified Rust mailbox service could use a transactional database for per-recipient ciphertext envelopes, minimal routing/expiry/quota metadata and authenticated service receipts; selection of its server datastore/driver, deployment and backup scheme is open. Local client state uses SQLite now; that does **not** mean the relay is a mailbox, that server SQLite has been chosen, or that stock SQLite encrypts either history or queue rows. No message can be uploaded as captured FM Noise stream ciphertext: the recipient must be able to decrypt **asynchronously** with a separately approved reviewed application-message E2EE scheme, sender authentication and a portable recipient/queue receipt design (`Identity_And_Encryption.md`, `Messaging_Protocol.md`). No HPKE, MLS, key provider or library is approved merely by availability in Rust.

Proposed later entry identity is `(deployment_id, recipient_device_id, sender_device_id, message_id)` plus authenticated immutable recipient ciphertext and sender/recipient scope, expiry and key IDs. A group event may produce different recipient ciphertexts under one logical ID. Server authenticates enrollment and current organization/project authorization at enqueue and fetch, bounds bytes/count/TTL and rejects same-key/different-content conflict. It commits ciphertext and ledger transactionally under an approved sync/backup policy **before** issuing an independently verifiable `mailbox_accepted` service receipt. Acceptance means durable queue storage, not delivery/read/task acceptance. If storage fails before commit, emit no acceptance. If it crashes after accepted commit, recover the entry. Recipient reconnects, reauthenticates, fetches bounded pages with replay-safe cursor/lease rules, validates/authenticates/decrypts and commits local inbox/dedup/receipt before device ACK; the server persists ACK and reconciles later sender status. ACK loss permits redelivery, never a second display. Malformed/undecryptable entries require bounded quarantine/error policy, not a false delivered receipt.

Revocation and membership changes demand a defined authoritative cutoff and policy on pending ciphertext. A removed recipient cannot fetch future content under current policy, but copies and keys already obtained cannot be erased. For later groups, commit an authorized recipient-device snapshot/version before any fanout; reject stale membership atomically, then optionally optimize via direct/live streams. Per-device ledger reports partial failures; a completed group ledger with failures is not “fully delivered.” Local sender expiry must not be extended silently by mailbox submission. Clock/skew, TTL start, retries, signed portable receipt authenticity, poison handling, quotas and backup/restore remain owner decisions.

## Validation/approval gates

- FM G1–G3: validate intended endpoint authentication through a separate relay, pre-forward reservation/source→destination denial, actual configured byte/duration/rate budgets, reservation renewal, quota and restart behavior; demonstrate two endpoint networks, a third relay, genuine direct-blocked automatic fallback and honest no-route when relay unavailable. Pin exact Rust crate APIs; no performance or universal NAT/egress claim without measured profiles.
- FM G2/G4: prove outbox-before-send, inbox/dedup-before-ACK, authenticated receipt and late-ACK reconciliation through ACK loss, restart and cross-path duplicates. Inspect relay buffers/logs/metrics for test plaintext/key sentinels within a declared boundary, and review library/session termination; a no-match scan is not a crypto audit.
- Later full-v0.1 gate: approve reviewed asynchronous E2EE, service/recipient signature and authorization semantics, server transaction/sync and backup policy, expiry/retention, cursor/replay and poison policy, quota figures, changed-key/revocation, group fanout and operator recovery; run offline reconnect/server-restart/expiry/denial tests before claiming MSG-04. Crate versions, key storage, confidentiality of database/WAL/backups, relay admission, limits and measured capacity remain unverified until tested.
